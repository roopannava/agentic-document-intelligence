01 What a Tool actually is

The single idea everything else follows from.

A tool is a description (a JSON schema) you advertise to the model — not a method, not code. Claude runs on Anthropic's servers, outside your JVM; it cannot call your Java, your DB, or anything. All it can do is produce text.

So "tool use" is a protocol, not a function call: Claude requests a tool (as text), and your code actually runs the work and returns the result. Think of it as an interface signature (what you publish) vs. the implementation (your method). Claude only ever sees and requests the signature.

Menu vs. kitchen: you hand Claude a menu (tool definitions); it writes an order ticket (tool_use); your code is the kitchen that cooks it (tool_result).

02 The tool spec — exactly three fields

What you send in the request's tools array.

FieldRequired?Purpose
nameYesThe label Claude calls it by, and the string you match in dispatch.
descriptionYes (in practice)How Claude decides when to use it.
input_schemaYesJSON Schema of the arguments. For a no-arg tool, an empty object.
// A no-argument tool — note: NO "id", NO "type"
{
  "name": "getMethodOne",
  "description": "Return all stocks.",
  "input_schema": { "type": "object", "properties": {} }   // empty = no args
}
  • A tool definition has no id — the id is generated by the server at call time.
  • A tool definition has no "type": "tool_use" — that appears only on the response block.
  • input_schema is required even with no arguments — use {"type":"object","properties":{}}.

03 The agentic loop & stop_reason

Claude's stop_reason drives your control flow. Read it once per turn, then branch.

loop:
  response = client.messages().create(messages, tools)   // one TURN = one call
  stop = response.stopReason()
  if stop == TOOL_USE:
      run the requested tool(s)
      append the assistant turn + a user message with tool_result(s)
      continue                                       // feed results back, loop
  else:  // END_TURN (or terminal) → done
      return the final text
stop_reasonMeaningYour move
tool_useClaude wants a toolRun it, return tool_result, loop
end_turnFinished naturallyStop — read the text
max_tokensHit the output capTruncated — continue/retry
stop_sequenceHit a custom stop stringPer your logic
refusalSafety declineHandle gracefully (don't read content)
pause_turnLong server-tool still runningResume the turn

Minimum correct loop: handle tool_use; let everything else mean "stop." You read stop_reason once into a variable — not a line per case.

04 The exchange: tool_use ↔ tool_result

A matched pair, linked by a correlation id — like request/reply messaging.

Claude sends →  { "type": "tool_use",    "id": "toolu_A",         "name": "getMethodOne", "input": {} }
You send back → { "type": "tool_result", "tool_use_id": "toolu_A", "content": "<stocks>" }
  • Same id, different field name: id on the tool_use, tool_use_id on the tool_result. You echo it verbatim — it's the correlation key.
  • content is a string. If your method returns an object/list, serialize to JSON first (only text crosses the wire).
  • The tool_result goes in a role: "user" message, not assistant.
  • "type": "tool_use" is a discriminator the server stamps on each response block so you know its kind (text, tool_use, thinking…).

05 Who creates what

Exam questions love to flip this. The boundary is the network.

Claude / the server

  • The message id msg_…
  • Each tool-call id toolu_… (fresh per call)
  • stop_reason
  • The "type" discriminator on each block
  • The decision of which tool to call & the input values

Your code

  • The tool definitions (name, description, schema)
  • The dispatch — match name → run the method
  • Echoing toolu_… back on the tool_result
  • Carrying the full conversation forward each turn
  • The max_tokens, model, system prompt

Rule of thumb: any underscore-prefixed id in a response (msg_, toolu_) was made by the server. You never generate ids.

06 Dispatch — name → method

The tool name is the routing key. Your code is the caller, not Claude.

// Keep the name in a constant so definition & dispatch can't drift
if (GET_METHOD_ONE.equals(name)) result = service.getMethodOne();   // YOUR code calls YOUR class
  • Tool name ≠ Java method name — independent. Only the declared name and the dispatch string must match.
  • name is a router (which method), not an argument. The argument is the tool's input.
  • Claude's tool_use is the trigger; your orchestrator is the actual caller — a plain in-JVM call.

07 Parallel tool use

One turn can contain several tool_use blocks. Run them concurrently — like threads.

  • Within a turn: independent tool calls run in parallel (an ExecutorService / parallelStream), then you join the results.
  • Across turns: strictly sequential — each turn needs the previous turn's results before deciding.
  • Hard rule: return all tool_results in one user message. Splitting them trains Claude to stop calling in parallel.
  • Your methods must be thread-safe (independent read-only queries are fine).

10 Workflow vs Agent · Structured output vs Tool

Workflow vs Agent

  • Workflow — code controls a fixed sequence (upload → extract → categorize). Deterministic steps.
  • Agent — the model decides which tools to call and when to stop. Use only when the task is open-ended.
  • Don't wrap deterministic steps (an S3 upload) in an LLM agent.

Structured output vs Tool

  • Both can return typed JSON that matches a schema.
  • If a tool existed only to force JSON back, prefer structured output.
  • Use tools when the model must trigger an action (your code runs something).
